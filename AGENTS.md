# Project rules

- Patient edits go through `usePatients.updatePatient`, which applies them locally first, persists only changed fields (`getChangedPatientFields`) and queues saves per patient; background refetch/realtime must not overwrite a patient with saves in flight. Why: full-object saves without this caused quick successive entries to overwrite each other.
- Releasing a vacant bed for a new patient must go through `releaseBedForFilling` / `RELEASED_BED_FIELDS` (`src/utils/releaseBed.ts`). Why: toggling `isVacant` alone brought back the previous occupant's birth date and admission dates.
- UE and UTI patient cards share the inline editors in `src/components/patient-card/InlineEditors.tsx` (sector-specific extras go through the optional `headerActions` / `renderItemActions` props, never hard-coded in the shared editor); UE wards render `EmergencyPatientCard` (the old `PatientCard.tsx` is kept only as reference until the new card is validated). Why: one editing behaviour across sectors makes UE→UTI transfer 1:1.
- UE→UTI transfer runs only through the `transfer_patient_to_uti` database function (copy to the UTI bed, free the UE bed, log the movement in one transaction). Why: a partial client-side transfer could duplicate or lose a patient.
- Browser checks against the preview must block every write request and fulfil it immediately (never delay inside the route handler). Why: a delayed handler let a test write reach real patient data when the browser closed.
- Phone layout (<768px) is written as base classes with `md:` restoring the desktop look; the phone top bar stays pinned through the mobile `.app-glass-header` rule in `src/index.css` (sticky works only because `main` scrolls with the window on phones), and patient-card actions come from one shared `actionControls` element shown in the side column on desktop and in the patient line on phones. Why: a phone fix must never change the desktop layout, and the card menus must not drift apart.
- Patient administrative AI recognition (name, birth date, prontuário, atendimento) runs only in the `extract-patient-admin-data` edge function and fills the shared `PatientInfoDialog` for review before saving; PRONT./ATEND. render through `patient-card/AdminIdentifiers` right after the age in UE and UTI cards. Why: the model must never write patient data without the doctor confirming, and both sectors must show the same identifiers.
